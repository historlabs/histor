# Sandbox inference profile v0.1

What a provider must ship for their system to be testable in the sandbox.

The contract is deliberately narrow. The sandbox does not care how the system works,
what it was trained on, or what runs inside the container. It cares that the container
answers a fixed request shape, returns a fixed response shape, logs what it decided,
and never initiates a connection to anything.

## 1. Delivery

An OCI image, referenced by digest, serving an **OpenAI-compatible HTTP API** on port
**8000**. This is the interface vLLM, SGLang, TGI, llama.cpp server, Ollama,
TensorRT-LLM, NVIDIA NIM and Triton's OpenAI frontend all expose, so for most
providers this profile is satisfied by configuration rather than code.

A secondary adapter for **Open Inference Protocol / KServe v2**
(`POST /v2/models/{name}/infer`) covers classic models served by Triton, KServe,
MLServer or OpenVINO Model Server. Same output fields, same logging duty. It is
implemented after the main path works.

## 2. Endpoints

The relay permits exactly three. Everything else is rejected and logged as evidence.

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/health` | 200 when ready to serve. Readiness only; no body contract. |
| `GET` | `/v1/models` | Lists **exactly one** model. More than one is a conformance failure: the sandbox tests a system, not a menu. |
| `POST` | `/v1/chat/completions` | The one request that carries work. |

## 3. Request

The harness sends a user message with one image content part as a base64 data URL,
plus a fixed text prompt it supplies. The prompt is pinned by digest in the plan,
because changing the prompt changes the system under test.

The request always carries `temperature: 0` and an integer `seed`. Both are recorded
in the attestation. A provider whose system ignores them will fail the determinism
test, which is the intended outcome rather than a limitation of the harness.

`response_format` is `json_schema`, with:

```json
{
  "type": "object",
  "properties": {
    "age": {"type": "number", "minimum": 0, "maximum": 120},
    "is_adult": {"type": "boolean"},
    "confidence": {"type": "number", "minimum": 0, "maximum": 1}
  },
  "required": ["age", "is_adult", "confidence"],
  "additionalProperties": false
}
```

`confidence` is not decoration. The accuracy guidance we work against expects an
output to carry a measure of its own uncertainty, and the harness uses it to report
calibration alongside accuracy.

## 4. What is never sent

Not as a courtesy, as a control. The model never receives:

- true ages
- demographic group labels
- file names, EXIF, or any image metadata
- dataset item identifiers

Every call carries an `X-Request-Id` the relay generates fresh. It correlates a
request with a response and with a log line. It correlates with nothing else, and
carries no information about which dataset the item came from or where in the stream
it sat. Items are shuffled and interleaved with decoys and repeats.

## 5. Response

The relay validates every response against the schema above and rejects anything
else — extra fields, non-JSON, oversized bodies — before the harness sees it. A
rejected response is recorded and counts against the run.

This is the control for "model hides data in responses". Extra fields are the obvious
channel out of an isolated container, and strict validation at the relay closes it
without the harness needing to be careful.

## 6. Decision logging (the Article 12 test)

The container writes **one JSON line per request to stdout**:

```json
{"ts": "2026-11-03T09:14:22.114Z", "request_id": "3f2b...", "output": {"age": 24.5, "is_adult": true, "confidence": 0.91}, "model_id": "demo-vlm", "model_version": "1.4.0", "latency_ms": 182}
```

| Field | Required | Why |
|---|---|---|
| `ts` | yes | RFC 3339, UTC, millisecond precision. |
| `request_id` | yes | Taken from the `X-Request-Id` header the relay set. Not generated by the container — a container-chosen id proves nothing about coverage. |
| `output` | yes | The structured result, as returned. |
| `model_id`, `model_version` | plan | Art. 12 expects the model and its configuration to be identifiable from the log. Cross-checked against the pinned digest. |
| `latency_ms` | plan | Performance and capacity data; cheap to emit and the first thing a post-market monitor wants. |

Which of the optional fields are mandatory is set per participation by the plan's
`decision_logging.required_fields`, not by this document.

The backend collects stdout for the run; the harness matches every `request_id` the
relay issued against the log. `min_log_coverage: 1.0` means every request appears.
The plan also records the retention the participant commits to
(`retention_months`, floor of 6 under Art. 19(1)).

**Logging is not a formality here.** A system that answers correctly and logs nothing
fails the sandbox, because a high-risk system that cannot be reconstructed after the
fact cannot be supervised after the fact.

## 7. Isolation obligations on the image

The container runs with a read-only root filesystem, a memory-backed `tmpfs` for
scratch, no mounted volumes, no service account token, and no network egress at all —
not to the relay, not to segment A, not to DNS, not to the internet. It accepts
inbound traffic only from the relay.

An image that needs to reach the network at startup — to fetch weights, check a
licence, phone home — **cannot be tested in this sandbox**. Everything the model needs
must be in the image. This is a real constraint on providers and it is not negotiable:
a model that can reach the internet during a run can exfiltrate the test data, and the
run proves nothing.

## 8. Conformance

`histor conformance`, published with the engine, runs a provider image locally and checks every requirement above, including the
logging contract and the isolation obligations. It is the provider's
pre-flight: an image that does not pass it will not pass the gate.

It must pass `mock-good` and flag `mock-evil` on the logging and schema violations
`mock-evil` deliberately commits.
